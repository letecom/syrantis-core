# Client Test Account Runbook

## Purpose

Create or promote one operator-controlled test user to `role = client` for validating the 023AJ
client app boundary.

Do not place plaintext passwords, password hashes, cookies, session tokens, API keys, or real
customer data in Git, tickets, screenshots, shell history, or implementation reports. Codex must
not mutate production data automatically.

## Current Tooling

Existing safe creation tooling is founder-oriented:

```bash
pnpm --filter @syrantis/api create-founder
make auth-create-founder
```

It creates an internal admin/founder validation user and is not a client-user manager. 023AJ does
not add a full User Manager or Admin Workspace Control Plane.

## Operator Path

Until dedicated user management exists, an operator may create or promote a test user manually in
the production database using approved operational access. Use placeholders in notes and commands;
do not paste real credentials into shared artifacts.

Required user state:

- email: placeholder test address controlled by the operator
- password hash: generated by the approved auth/password path
- workspace: the intended test workspace
- status: `active`
- role: `client`

If promoting an existing user, verify that only the intended test user changes role. Do not promote
founder/admin/operator accounts used for production operations.

Future required product work: add a User Manager/Admin Workspace Control Plane so operators can
create client users without manual database intervention.

## Verification

After deployment and the `app.syrantis.fr` Caddy site block are in place:

1. Open `https://app.syrantis.fr/login`.
2. Log in as the `role = client` test user.
3. Confirm `/inbox` renders the live Client Inbox.
4. Confirm `/dashboard` renders the client placeholder.
5. Confirm `/config` renders the client placeholder.
6. Confirm the client shell navigation shows only:
   - Tableau de bord
   - Boîte de réception
   - Configuration
7. Confirm client navigation does not show Ops, API Keys, Google Sheets, Pushback, Mail Queue,
   Draft Queue, Gmail Export admin, Client Inbox Lab, Response Policy admin, raw JSON/debug labels,
   or send/reply/forward controls.
8. Confirm client Inbox API routes work for the same session:
   - `GET /api/client/inbox/messages`
   - `GET /api/client/inbox/messages/:mailItemId`
   - `PATCH /api/client/inbox/messages/:mailItemId/draft` when existing action rules allow editing
   - `POST /api/client/inbox/messages/:mailItemId/gmail-export-request` when existing action rules allow request
   - `POST /api/client/inbox/messages/:mailItemId/gmail-export-cancel` when existing action rules allow cancel
9. Confirm admin-only routes return `403` or equivalent blocking behavior for the client session:
   - `/api/admin/ops/health`
   - `/api/workspace-api-keys`
   - `/api/integrations/google-sheets/setup-status`
   - `/api/integrations/google-sheets/setup-test`
   - `/api/workspace-context`

Do not include raw response bodies if they contain sensitive data. Record only pass/fail,
status codes, timestamps, and safe route names.
